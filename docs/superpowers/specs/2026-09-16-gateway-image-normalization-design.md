# Gateway 图片标准化与识别容错设计

## 背景与目标

App 图片可成功上传并绑定消息，但 Gateway 的默认多模态调用在数百毫秒内失败；同一原图使用同一 Grok 4.6 配置直调可成功。现有实现会把所有上游异常改写成“未配置识图模型”，无法区分配置错误、图片兼容问题和上游故障。

目标是让相册图片以稳定、低延迟、不泄露 EXIF/GPS 的方式送入模型，并为失败保留可诊断但不含敏感信息的记录。

## 处理流程

`AttachmentContentService` 读取当次提问原图后，使用 Sharp 执行自动旋转、最长边限制为 `1600 px`、转换为质量 `85` 的标准 JPEG。输出不复制 EXIF、GPS 或原始 ICC 元数据。该内存结果同时供“当前模型直接识图”和“默认多模态模型先识别”两条路径使用。用户原图不改写，会话完成或失败后仍按现有规则立即释放。

## 容错与诊断

多模态调用只在明确的连接错误、HTTP `429` 或 `5xx` 时立即重试一次；其他 `4xx` 和图片预处理失败不重试。记录内容限定为附件 ID、字节数、标准化后尺寸、耗时、异常类型、HTTP 状态和供应商错误码；不记录 API Key、Base64、图片内容、原始路径或供应商响应正文。

模型密钥沿用普通会话的 Anthropic 兼容约定，通过 `Authorization: Bearer` 发送；图片识别链路不得另行改用 `X-Api-Key`，避免同一模型在文字会话可用而图片请求返回 `401`。

App 保持现有协议。服务端将“未配置”与“已配置但上游不可用”分开，后者返回可重试的识图服务失败提示。

## 验证

- 单元测试验证旋转、尺寸上限、JPEG 输出和 EXIF/GPS 移除。
- 多模态路由测试验证标准化图片、可重试错误仅重试一次、非可重试错误不重试。
- 会话测试验证附件绑定、事件结束和原件释放不受影响。
- 部署后用真机重新选择图片，确认图片回答完成、会话恢复 `idle`，且 Gateway 日志不含敏感数据。

## 非目标

不改变相册选择交互、附件数量与大小限制、模型切换规则、历史缩略图或工作区文件。本阶段不重新打包 App。
